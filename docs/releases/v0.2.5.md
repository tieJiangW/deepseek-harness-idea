# DeepSeek Harness for IntelliJ IDEA — v0.2.5

## English

### Highlights

- **Install a dsh plugin package once, and every project loads it.** dsh plugins used to be per project because each
  project has its own `DSH_HOME`; now every project's `profiles/` directory is linked to one shared profile root.
  Sessions, workspaces and attachments still live in each project's own `DSH_HOME`, so isolation is unchanged.
- **A new "DSH Plugins" page** (and a tool window title-bar action) to list, install, and remove dsh plugin packages.
  dsh's own Web UI has no install entry point — its plugin inventory is read-only.
- **You can see what is happening while it installs.** A live progress bar, a per-second elapsed timer, the current
  phase ("preparing pnpm", "installing …"), streamed pnpm output, a "still running" hint when the child is silent,
  a Cancel button, and an explicit green ✓ / red ✗ result (with the time taken) plus an IDE notification. The first
  run also downloads a private pnpm, so the phase text explains that it needs network.
- **No global pnpm required.** The plugin provisions a private pnpm under the shared config home on first use.
- **Safe migration and rollback.** Existing per-project profiles are moved to
  `<shared home>/profiles-migrated/` (never merged, never deleted), and the profile manifest is backed up before every
  install/remove and restored if the command fails.

### Why plugins were not shared, and what changed

dsh resolves a profile as `$DSH_HOME/profiles/<name>`, and plugin packages are installed into that profile's
`node_modules`. Because the plugin gives every project its own `DSH_HOME` (for per-project sessions and workspaces),
`dsh plugin --profile web add <pkg>` only ever landed in the current project.

v0.2.5 links **only the `profiles` directory** of each project to `<shared config home>/profiles`:

- install a package in any project → it is visible in all of them;
- `sessions` / `storages` / `attachments` stay in each project's `DSH_HOME`, so project isolation does not regress;
- the link is created idempotently (Windows junction, elsewhere a symlink); a link pointing elsewhere is repaired;
- a project that still has a real per-project profile is migrated: the shared profile is seeded from it first (missing
  files only — the shared copy always wins), then the whole directory is **moved** to
  `<shared home>/profiles-migrated/<hash>/` and the link created. If anything fails, the directory is moved back and
  that project simply keeps using its own profile — a shared-plugin feature must never stop dsh from starting
  (dsh fails loudly when a profile cannot be loaded).

Turn it off in *Settings → Tools → DeepSeek Harness* ("Share dsh plugin packages across projects", on by default).
Turning it off unlinks the directory and keeps the shared root intact; plugins installed while sharing was on stay in
the shared profile, so re-enabling restores them.

### Installing plugins

Installation forwards to dsh's own `dsh plugin --profile web add …` instead of calling pnpm directly, because dsh also
(a) initializes the profile from its template, (b) anchors relative specs, and (c) rewrites `dsh.profile.bundles` after
the install — resolving the real installed package name even for `link:`/git/tarball specs. The only prerequisite is a
`pnpm` on `PATH`, so the plugin installs a private copy (`pnpm@9.15.9`) into `<shared home>/plugin-tools/` using the
bundled npm and prepends its shim to the child `PATH`. Nothing is written to the runtime tree or your global
environment.

Accepted specs: package names with an optional version range (`@scope/plugin@^1.2.0`) or an **absolute** local path
(`link:/abs/path`). Whitespace and shell metacharacters are rejected — dsh forwards arguments through a shell on
Windows, where `a&b` is truncated and `^` ranges are mangled unless quoted (the plugin quotes `^` ranges
automatically). Restart the harness (Restart in the tool window title bar) to load or unload a plugin.

### Progress feedback

`pnpm add` can be silent for tens of seconds while it resolves and downloads, and the first run also has to fetch a
private pnpm — which is exactly when you need to know whether it is working or stuck. The page therefore shows:

- an indeterminate progress bar plus a per-second "phase (Ns)" timer, and the phase itself
  (checking the runtime → preparing pnpm → installing);
- streamed command output (throttled to 150 ms refreshes, capped at 4000 lines);
- a "no output for Ns, still running…" hint driven by a 2-second heartbeat from the child process;
- a Cancel button that kills the child and restores the profile manifest;
- an unambiguous result: green `✓ … (took Ns)` or red `✗ reason`, the same line appended to the output area, and an
  IDE notification (so you still see it if you switched away).

### Assets

- `deepseek-harness-idea-0.2.5.zip` — plugin (thin: the runtime downloads on first use, SHA-256 verified).
- `runtime-<os>-<arch>.zip` + `.sha256` — prebuilt runtimes for Windows x64, macOS arm64/x64, Linux x64/arm64.
  Use these to stay offline: *Settings → Tools → DeepSeek Harness → Choose local runtime zip…*

### Compatibility

IntelliJ IDEA 2024.1 – 2026.2 (`since-build=241`, `until-build=262.*`). dsh 0.1.5-rc.2 (Node.js 22.23.2).

### Fixes in this release

- **Reinstalling after an uninstall no longer fails with
  `ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF`.** The profile's `node_modules` had been created by a different
  pnpm configuration (dsh's module-fallback healing, or an older build), and pnpm refuses to operate on it. The
  installer now reads `virtualStoreDirMaxLength` from `node_modules/.modules.yaml` and passes the same value to pnpm
  (verified against a real pnpm: without it the command fails exactly as you saw, with it the install succeeds). If
  pnpm still reports a mismatched modules directory, the old one is renamed to `node_modules.broken-<timestamp>` and
  the command is retried once, so the directory is rebuilt instead of making you do it by hand.
- **Uninstalling no longer hangs or fails because the harness is running.** Two separate causes: (a) the progress
  updates from the background worker were posted with the default modality state, which is `NON_MODAL` on a
  background thread — so inside the modal Settings dialog they were deferred until the dialog closed (the command had
  actually finished after one second, but the panel kept counting seconds); and (b) `pnpm remove` has to delete files
  from `node_modules`, which the running harness holds open, so it reliably exited with code 1. Background → UI
  updates now use `ModalityState.any()`, and a failed uninstall falls back to removing the package from the profile
  manifest (dsh decides what to load from `dsh.profile.bundles`, so the plugin is genuinely uninstalled and simply
  stops loading after a restart; leftover files are reconciled by the next pnpm operation).
- **Install/remove/repair run on the plugin's own worker thread** instead of the IDE's shared pool. Right after a
  restart the pool can be saturated by indexing, which left our task queued with no rejection, no error and no log —
  i.e. "nothing happens".
- **A v0.2.5 development build could delete your installed plugins.** The legacy-cleanup step (which also runs on every
  start and every Refresh) still listed `<shared home>/profiles` as a v0.1.2 leftover — but since v0.2.5 that directory
  *is* the shared profile, i.e. where your plugins live. The result was a Refresh that appeared to hang for tens of
  seconds (recursively deleting tens of thousands of `node_modules` files) and then a plugin list that had gone empty.
  The directory is no longer cleaned, and a regression test now asserts the shared profile, its `node_modules` and the
  installed packages survive cleanup.
- **Refresh no longer runs the full startup initialisation.** It used to call `ensureHome` (config migration, MCP script
  deployment, legacy session migration, cleanup) just to read a profile manifest. It now reads on the EDT (measured at
  ~3 ms) and only repairs in the background when the profile is not ready yet.
- **The "no output" hint no longer lies.** It only appears while a child process is actually running; reading a profile
  gets a neutral "still reading" message (a first-time migration can be slow), and the elapsed timer no longer invites
  you to press a Cancel button that is not even shown.
- **The shared-config migration marker stores a layout version**, not the plugin version — so upgrading the plugin no
  longer re-runs the one-off config migration on every start.

## 中文

### 重点

- **dsh 插件包装一次，所有项目都加载。** 此前因为每个项目有独立 `DSH_HOME`，插件是"每项目一份"；现在每个项目的
  `profiles/` 目录都链接到统一的共享 profile 根。会话、工作区与附件仍在各自 `DSH_HOME`，**项目隔离不变**。
- **新增「DSH 插件」设置页**（以及工具窗标题栏动作）：查看、安装、卸载 dsh 插件包。dsh 自己的 Web UI 没有安装入口
  （其插件清单是只读的）。
- **安装过程看得见**：进度条 + 每秒刷新的用时 + 当前阶段（准备 pnpm / 正在安装）+ 实时 pnpm 输出 +
  长时间无输出时提示"仍在运行" + 可取消 + 结束给出绿色 ✓ / 红色 ✗（含用时）并弹 IDE 通知。
  首次安装会先下载私有 pnpm，阶段文案会明确提示需要联网。
- **不需要全局 pnpm**：首次使用时在共享配置目录下准备一份私有 pnpm，不污染用户环境。
- **迁移与回滚安全**：既有的项目级 profile 会被移动到 `<共享根>/profiles-migrated/`（不合并、不删除）；
  每次安装/卸载前备份 profile manifest，命令失败自动回滚。

### 为什么插件此前不共享，改了什么

dsh 把 profile 解析为 `$DSH_HOME/profiles/<name>`，插件包装进该 profile 的 `node_modules`。由于插件为每个项目
准备独立 `DSH_HOME`（为了会话与工作区按项目隔离），`dsh plugin --profile web add <pkg>` 只会装进当前项目。

v0.2.5 把**每项目的 `profiles` 目录**链接到 `<共享配置根>/profiles`：

- 在任一项目安装 → 所有项目可见；
- `sessions` / `storages` / `attachments` 仍在各自 `DSH_HOME`，项目隔离不回归；
- 链接幂等创建（Windows junction，其它平台符号链接）；指向错误的链接会被修正；
- 仍在使用独立 profile 的项目会被迁移：先以它**播种**共享 profile（只补缺失文件，共享侧优先），再把整份目录
  **移动**到 `<共享根>/profiles-migrated/<hash>/` 并建立链接。任一步失败则把目录移回，该项目继续用独立 profile ——
  共享插件是增强能力，绝不能因此让 dsh 起不来（dsh 对 profile 加载是 fail-loud）。

可在 *设置 → Tools → DeepSeek Harness* 的「跨项目共享 dsh 插件包」开关关闭（默认开启）。关闭只断链、共享根不删；
共享期间装的插件仍留在共享 profile，重新开启即恢复。

### 如何安装插件

安装转发给 dsh 自己的 `dsh plugin --profile web add …`，而不是直接调 pnpm —— 因为 dsh 还会
(a) 按模板初始化 profile、(b) 锚定相对路径规格、(c) 安装后重写 `dsh.profile.bundles`（按**实际装出来的包名**，
`link:`/git/tarball 规格也正确）。唯一前置条件是 `PATH` 里有 `pnpm`，因此插件用运行时自带的 npm 把私有
`pnpm@9.15.9` 装到 `<共享根>/plugin-tools/`，并把其 shim 前置到子进程 `PATH`。不写运行时树，也不改全局环境。

可接受的规格：包名 + 可选版本范围（`@scope/plugin@^1.2.0`）或**绝对路径**本地规格（`link:/绝对/路径`）。
空白与 shell 元字符会被拒绝 —— Harness 在 Windows 上经 shell 转发参数，`a&b` 会被截断、`^` 版本范围不加引号会被
吃掉（插件对 `^` 自动加引号）。安装/卸载后请在工具窗标题栏点「重启 Harness」加载。

### 安装进度反馈

`pnpm add` 在解析/下载依赖时可能几十秒不打印任何东西，而首次还要先下载一份私有 pnpm —— 恰恰是最需要知道
"在干活还是卡死"的时刻。因此设置页会显示：

- 不定进度条 + 每秒刷新的"阶段（已 N 秒）"，阶段本身是：检查运行时 → 准备 pnpm → 正在安装；
- 实时流式输出（150ms 节流刷新，最多保留 4000 行）；
- 子进程每 2 秒一次心跳驱动的"已 N 秒无输出，仍在运行…（可取消）"提示；
- 「取消」按钮：杀掉子进程并回滚 profile manifest；
- 明确结果：绿色 `✓ …（用时 N 秒）` 或红色 `✗ 原因`，同一行也会写入输出区，并发 IDE 通知（切走窗口也能看到）。

### 本版修复

- **卸载后重新安装不再报 `ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF`。** profile 的 `node_modules` 曾被**另一套
  pnpm 配置**创建（dsh 的模块自愈、或旧构建），pnpm 拒绝在上面继续操作。现在安装/卸载前会读
  `node_modules/.modules.yaml` 里的 `virtualStoreDirMaxLength`，把同值传给 pnpm（真实 pnpm 已验证：不传时与你看到的
  报错完全一致，传了就安装成功）。若 pnpm 仍报告目录不一致，则把旧目录改名为 `node_modules.broken-<时间戳>`
  并自动重试一次，替你完成重建。
- **卸载不再因为 Harness 在运行而卡住或失败。** 两个独立原因：① 后台线程回报进度时用的是默认模态状态，
  而后台线程的默认值是 `NON_MODAL` —— 在**模态**的设置对话框里会被推迟到对话框关闭才执行（命令其实 1 秒就
  结束了，界面却一直在读秒）；② `pnpm remove` 必须删除 `node_modules` 里的文件，而运行中的 Harness 正持有
  这些文件，于是稳定 `exit=1`。现在后台 → UI 的更新统一用 `ModalityState.any()`；卸载失败时兜底改为**从
  profile manifest 移除声明**（dsh 按 `dsh.profile.bundles` 决定加载什么，所以插件确实被卸载、重启后不再加载；
  残留文件会在下次 pnpm 操作时对账）。
- **安装/卸载/修复改到插件自建的专用线程**，不再占用 IDE 公共线程池：刚重启 IDE 时索引会占满该池，导致我们的
  任务排队且**不报错、不打日志**——表现就是"点了没反应"。
- **v0.2.5 的开发中构建可能删掉你已装的插件。** 遗留清理步骤（启动与「刷新」都会跑）仍把
  `<共享根>/profiles` 当成 v0.1.2 残留 —— 但从 v0.2.5 起这个目录**就是**共享 profile，插件全在里面。
  表现是：点「刷新」后像卡住几十秒（正在递归删除上万个 `node_modules` 文件），随后插件列表变空。
  现已不再清理该目录，并新增回归测试断言"共享 profile / 其 `node_modules` / 已装插件在清理后必须存活"。
- **「刷新」不再跑完整的启动初始化**：以前为了读一个 manifest 会调用 `ensureHome`（配置迁移、MCP 脚本部署、
  legacy session 迁移、遗留清理）；现在直接在 EDT 上读（实测约 3ms），只有 profile 尚未就绪时才转后台修复。
- **"无输出"提示不再误导**：只有真的在跑子进程时才显示；读取 profile 用中性的"仍在读取"文案
  （首次迁移可能较慢），也不会再提示去点一个没显示的「取消」按钮。
- **共享配置迁移标记改存布局版本**（而非插件版本），升级插件不会再每次启动都重跑一次性迁移。
